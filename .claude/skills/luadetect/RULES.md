# luaDetect 規則

每一條都對應一次**實際發生過**的錯誤。沒發生過的通則不寫在這裡。

---

## A. 掃描與回報

**A1. `error` 的意思是「會炸」，不是「寫得不對」。**
判準是「這行跑起來會不會 crash 或明確壞掉」。不確定就是 `warn`。
改規則時如果讓某個「只是寫法不好」的情況變成 `error`，那是改壞了。

**A2. 跑得起來的專案裡出現 `error`，預設它是誤報。**
使用者說過「目前專案中的基本上都是可運作的」——這是最強的 oracle。
照這個假設查過一次，50 筆 `error` **全部**是誤報。
逐筆開原始碼確認，不要因為規則邏輯看起來對就相信它。

**A3. 誤報比漏報糟。** 誤報會叫人去改本來正確的程式碼，並且讓整個工具失去信任。
任何取捨往「少報」倒。

**A4. 「查不出來」不等於「有問題」。**
對不到 `.csd`、讀不到檔案、名字是動態組出來的 → 跳過並計入涵蓋率，不要猜。

**A5. 回報時一定要附涵蓋率。** 「沒有回報」不可以被讀成「都對」。
`summaryTable` 原樣貼出，不要只講數量。

**A5b. 涵蓋率的每個數字都要有分母，而且「檢查了 + 沒檢查 = 總數」要對得起來。**
「資源路徑判斷 7」沒有分母時，看的人分不出是「7 條全驗過」還是
「7 條驗過、另外 40 條沒交代」——沒有分母的涵蓋率表**沒有回答它自己要回答的問題**。
實測：資源那條規則原本把 1147 條動態路徑直接 `continue` 掉，全庫 2541 條裡
表上只交代了 1394 條，差額不在任何地方。「不猜」的那一類**也要計數**（A4 就是
這樣寫的：跳過並計入涵蓋率）。

**分母要由規則自己報，不能從子字串猜。** 用 `"getChildByName" in code` 當分母，
規則卻還認得別的取用寫法，算出來是「完成 574 + 跳過 32 = 606 > 分母 605」。
分母要跟規則的守門條件共用同一個函式（`has_node_access`）。

**A5c. 「沒檢查」的原因要分類，不能給一個籠統的總數。**
`Item` 模組 700 條資源路徑裡 690 條沒檢查，表上原本只寫「動態組出來的 690」，
讀的人合理推論成「檔名是 `string.format` 拼的，靜態看不到」——實測**只有 1 條**
是格式樣板，其餘 689 條是 `Protocol.lua` 裡寫死的完整檔名（`img_cash.png`），
只差前面接一個常數前綴。籠統的標籤會產生**看起來有根據、其實是錯的**結論，
比沒有標籤更糟。現在分成「要接前綴的檔名片段 / 格式樣板 / 對不到資源根」。

順帶記著這個結論：那 689 條**就算拼出完整路徑也不該報**。`item/img/` 磁碟上
只有 4 個 png，其餘在整個資源樹與所有 plist 裡都不存在——拼起來會產出 683 筆
沒人能處理的警告。**涵蓋率的數字變好看不等於檢查變有用**；要提高涵蓋率之前，
先確認提高之後報出來的東西是可行動的。

**A6. 不要引用上一次的結果。** 工具被擋住、指令沒跑成功的時候，說「沒跑成」。
換一條路徑先試（Bash 被擋 → 用 PowerShell 工具），還是不行才請使用者代跑，
而且要明講「以下是還沒驗證的推測」。

**A7. 每個斷言都要有對應的指令輸出。**
講錯過的例子：說 `coin_test.plist` 不存在（它在 `cocosstudio/effect/`）、
算錯 dispatcher 呼叫點數量。兩次的原因都是「沒有實際查就下結論」。

**A8. finding 多一筆少一筆，要查出「確切是哪一段造成的」，
不要拿最近改的那條規則去解釋。**
`PlayInfo.lua:86` 那筆消失被歸因給剛加的雙向別名（B5），實際原因是接收者
`pageView:` 判定成 widget 監聽——同一個檔案裡兩件不相干的事，看起來卻很像。
順著實際查下去才發現真正的 bug（C9）。
歸因錯誤的成本不只是講錯話：它會讓一個還在的缺陷被當成已經解決。

**A9. 「檔案在等待期間被改掉了」要用 mtime／`git log`／`git status` 確認**，
不要當成預設解釋。這次查出來是 mtime 一個月前、工作目錄乾淨——是工具變了。
反過來也一樣：全庫數字自己變了（`NODE_MISSING` 58→57）先查輸入有沒有變，
`find <lua_root> -name "*.lua" -newermt "-1 day"` 一秒就知道。這次確實是
Inanna 的 `.lua` 被改過，不是工具不決定性。

**A10. 在真實檔案上注入 bug，還原後要驗 sha256，`git status` 乾淨不算數。**
Inanna 的 `.lua` 是 **CRLF**，`sed -i` 會把整個檔案轉成 LF；git 的 autocrlf
讓 `git status` 看起來乾淨，但檔案的位元組已經全變了。
流程：`cp` 一份原檔 → `sha256sum > 檔` → 注入 → 掃描 →
`cp` 備份回去 → `sha256sum -c` → `cmp`。三個都過才算還原。

## B. 改或加規則

**B1. 「修好之後 0 筆」必須注入一個真 bug 驗證還抓得到。**
修錯正則會把 26 個誤報變成 24 個漏報——兩者都顯示「0 筆」。

**B2. 跑全庫要比對 finding 集合的差異，不是比數量。** 數量一樣不代表內容一樣。
全庫不變量放在 `tests/test_project.py`（釘住**具體是哪幾筆** error，專案不在
就自己跳過）。**不要**再寫成臨時腳本裡的「全庫 0 筆 error」——那種寫法每次加規則
就過期，而過期的樣子跟「工具壞了」一模一樣，每次都要重新判斷是哪一種。

**B3. 加規則前先 `grep` 一次「這個 API 名字有沒有更長的親戚」。**
`addEventListenerWithFixedPriority` 整塊漏檢，就是因為舊正則要求
`addEventListener` 後面緊接 `(`，而它們前綴相同。同前綴 API 是這個專案的常見盲區。

**B3b. 「配對」規則要去看 C++ 標頭，把「解除」的所有寫法查齊——
不能只收專案裡看得到的那幾種。**
`cc.EventDispatcher` 有五個 remove，而且**不是每一個都拿 listener 物件**：

| 寫法 | 拿什麼 |
| --- | --- |
| `removeEventListener( listener )` | 物件 |
| `removeEventListenersForTarget( node )` | 節點 |
| `removeAllEventListeners()` | 全部 |
| `removeEventListenersForType( type )` | 整個型別 |
| `removeCustomEventListeners( 事件名 )` | **事件名** |

只收前三個的代價：全庫 5 筆 error 全是誤報，而且訊息斷言「已經不可能解除」
——把完全正確的程式碼指成必須重寫。**訊息裡不要對「做不到」下斷言**，
你只知道「這個檔案裡沒看到某幾種寫法」，不知道「沒有別的辦法」。

查法：`grep -nE "void remove[A-Za-z]*\(" <對應的 .h>`。
Cocos 的標頭在 `Mangan_git/Cocos2d-x/cocos/`。

**B4. 改完要一起更新：** `RULES` 字典、`README.md` 的規則表與分級表、
`report.py` 的 `_WHY`／`_CONTEXT`、迴歸測試（測試裡寫清楚對應哪個真實案例）。

**B5. 名字比對要考慮雙向別名。**
註冊寫 `local listener`、解除寫 `self.m_x`，中間靠 `self.m_x = listener` 連起來
（`PlayInfo.lua` 就是這樣）。單向別名解析會對不到而誤報，要用等價類（union-find）。

## C. 程式碼陷阱

**C1. `luasrc.expr_before()` 回的字串含尾端分隔符**（`dispatcher:`、
`getEventDispatcher():`）。用 `$` 收尾的接收者正則要容許 `[:.]?\s*$`，
否則一處都對不到，而且**沒有任何錯誤訊息**。

**C2. `grep` 找 API 名要帶 `(`，而且要 `-i`。**
`grep "addEventListener"` 會前綴命中 `addEventListenerWithSceneGraphPriority`；
`grep "ScheduleScriptFunc"` 則**對不到** `node:scheduleScriptFunc(`（首字大小寫不同），
於是把「這個檔案有 1 次原生排程」數成 0 次。兩種方向都犯過。
用 `grep -niE "名字\("`，並且**拿工具自己的輸出對照**（`explain` 會講「原生 N 次」）
——兩邊不一致時，先懷疑自己的 grep。

**C3. 快取「完整資料」再過濾，不要快取「過濾後的結果」。**
`_module_code` 曾被第一次查詢的名字污染，之後每個名字都拿到錯的語料。

**C4. 讀不到檔案 ≠ 檔案是空的。** 要往上傳成 `unreadable` 並降級嚴重度，
不要 `except: return ""`。

**C5. 訊息與長度限制在 `Finding.__init__` 收斂**，不要叫每條規則自己記得——
漏一條就壞一次表格排版。

**C6. 效能改動前後都要量，並比對 finding 有沒有漂移。**
自己做過三次「優化」反而變慢（2.07→2.41s、3.2→45s、6.03→7.67s）。

**C6a. 量之前要暖機。** 第一組跑的規則會付掉整個 `.csd` 索引與名稱快取的
建置成本——沒暖機時 `nodes` 量出 13.7 秒，實際是 4.6 秒。
做法：先完整跑一次不計時，之後每項取多次最小值。

**C6b. 把工作往後推之前，先確認被呼叫端不會無條件重算。**
把 `consts` 改成惰性計算（只有用得到的檔案才算）之後**變慢** 6.03→7.67s：
`resources` 的 `check` 與 `stats` 是在函式開頭無條件算常數的，傳 `None`
反而讓它們各算一次，2 次取代 1 次。要惰性就得兩端一起改。

**C6c. A/B 用同一個行程裡的 monkeypatch，不要靠「改之前跑一次、改之後跑一次」。**
Inanna 的 `.lua` 會被人改（實測跨兩次量測之間就變了），兩次量測的輸入根本不同。
同行程 A/B 還能順便斷言「兩條路徑的 finding 集合完全相同」。

**C7. 快取要能被重置。** MCP server 是長駐的，每個掃描入口都要呼叫
`reset_caches()`，否則跨次掃描拿到舊資料。失敗的建構結果不要寫進快取。

**C8. 路徑要夾在根目錄內。** `_module_dir` 曾爬到 `C:\` 然後 `os.walk` 整顆硬碟。

**C9. 等價／別名關係一定要排除 Lua 字面值（`nil`、`true`、`false`）。**
`X = nil` 是**清除**，不是「X 跟 nil 指同一個物件」。當成等價的話，同一個檔案裡
每個被 `= nil` 清掉的東西都會併進同一類，解除其中一個就等於解除全部。
實測全庫 **529 個檔案**會這樣併（`PlayInfo.lua` 把 `touchBeganPos`、
`touchListener`、`self.m_pageViewLoopTouchListener` 併成一類）。
數字與字串不會被識別字正則吃到，所以只要擋這三個關鍵字（`_LITERAL`）。

推廣：**任何「合併成同一類」的關係，先問哪些值是不該被合併的哨符。**
這類 bug 的症狀是漏報，全庫 finding 總數可能一筆都不變（這次就是 192→192），
所以**不能靠總數變化發現它**——要直接把等價類印出來看。

**C10. 優先序不等於免驗證：明確給的輸入一定要先確認它存在。**
`projects.resolve()` 的優先序是 `path` → `project` → cwd，於是在 Inanna 目錄下跑
`luadetect voucherCenter --project NoSuchProj`，`path` 先解析成功，
打錯的專案名**從頭到尾沒被驗證過**，結果拿 cwd 的專案掃完回報「通過、離開碼 0」。
CI 裡一個 typo 就變成「檢查過了」——對檢查工具來說這是最不能有的失敗方式。
修法是把明確輸入的驗證**提到優先序判斷之前**，優先序本身不動。
（同一形式從 luaDetect 目錄跑會正確報錯，所以這種 bug 只在特定 cwd 下出現，
測試要把 cwd 與參數形式一起排列組合過。）

## D. Windows / 環境

**D1.** `os.replace` 在並行讀取下會 `PermissionError` → 要重試；暫存檔名帶 pid。

**D2.** Git Bash 裡 `cmd /c` 會被改寫成 `cmd C:/`，要寫 `cmd //c`。

**D3.** console 是 cp950，subprocess 的輸出要明確指定 encoding，
表格對齊用 `unicodedata.east_asian_width`（`len()` 對 CJK 會歪）。

**D4. 不要用 shell heredoc 直接貼含正則或 f-string 的 Python。**
heredoc 裡的 `\n` 會變成真正的換行 → SyntaxError。用 Edit 工具，或先寫檔再跑。
（這一條犯了 6 次。）

**D5. 新增任何寫檔的功能，寫入必須是原子的或獨佔的。**
多開 agent 是這個工具的常態用法。既有的寫入點都走
「pid 暫存檔 → `fileio.replace_atomically`」；**新加的 `bind --out` 一開始寫成
「先 `os.path.exists` 再 `open("w")`」，那中間有空隙**——兩個 agent 同時跑會兩邊
都通過檢查然後互相蓋掉，產出半截的 Lua。改用 `open(path, "x")`：存在性判斷與
建立是同一個系統呼叫，沒有那個空隙。
實測 10 個行程搶寫同一路徑 → 1 個成功、9 個乾淨失敗、檔案完整。

**D6. 併發測試要壓到「寫入」那條路，不是只壓讀取。**
第一次壓力測試 120 次操作全綠，但 `.csd` 沒變、所有行程都走名稱快取的**讀取**，
寫入路徑一次都沒跑到。要把 `HOME` 指到空目錄才強制得到重建
（`CSDVIEW_PROJECTS` 要另外指回真的登錄檔，不然連專案都找不到——
HOME 一搬，`~/.csdview_projects` 也跟著不見了）。

**D7. 併發 harness 的判定標準要先想清楚，不然會把正確行為當成失敗。**
壓力測試報「3 次非預期離開碼、4 次產出被截斷」，逐一查完全是 harness 的錯：
搶寫 `--out` 的輸家回離開碼 2 **就是正確行為**，而 `--out` 的內容寫進檔案、
stdout 當然沒有那段 Lua。真正的訊號（半截 JSON、traceback、檔案被截斷）
全都是 0。
